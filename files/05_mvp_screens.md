# RevGuard — MVP Screens

## Screen 1 — Merchant Dashboard

### Purpose
Show financial impact immediately.

### Must contain

```text
Revenue At Risk       ₹X
Revenue Recovered     ₹Y
Recovery Rate         Z%
```

Then:

```text
Root Cause Breakdown
- Temporary failure
- Insufficient funds
- Credential expired
- Mandate inactive
- Unknown
```

Then:

```text
Policy Decisions
AUTO
QUEUE_FOR_REVIEW
BLOCKED
```

Then a recovery-case table.

### Manual owner check
The top metrics must be generated from the database/evaluation run, not hard-coded.

---

## Screen 2 — Recovery Case Table

Columns:

```text
Transaction
Customer
Amount
Failure Cause
Confidence
Policy
Status
```

Filters:

- AUTO
- QUEUE_FOR_REVIEW
- BLOCKED
- RECOVERED
- FAILED

Search by:
- transaction ID
- customer ID

### Manual owner check
Test every filter and ensure counts match the visible rows.

## Screen 3 — Recovery Case Detail

### Header

```text
Transaction #TXN_123
Recurring Payment
₹4,999
```

### Diagnosis section

```text
Root cause:
Temporary failure

Confidence:
96%

Method:
Deterministic
```

For AI-classified cases:

```text
Method:
Gemini
```

### Policy section

```text
Retryable              ✓
Retry count < 3        ✓
Amount < threshold     ✓
Customer opted in      ✓
Payment not successful ✓

Decision:
AUTO
```

### Why did we act?

Show 3–5 deterministic reasons.

### Why did we NOT act?

For blocked/review cases, show the exact reason.

### Action section

```text
Action:
Recovery Payment Link

Provider:
Razorpay Test Mode

Status:
Created / Sent / Recovered / Pending
```

### Audit trail

Chronological timeline:

```text
10:04:12 Event received
10:04:12 Diagnosis completed
10:04:12 Policy evaluated
10:04:13 Payment link created
10:04:14 Message generated
10:04:15 Message sent
10:05:23 Payment recovered
```

## Screen 4 — Review Queue

Purpose:
Show bounded autonomy.

Cards:

```text
42 Cases Need Human Review

Reason distribution:
- High amount
- Low confidence
- Retry limit
- Ambiguous state
```

Each row has:
- amount
- diagnosis
- confidence
- policy reason
- Approve
- Reject

### Manual owner check
Approving a case must re-run state/idempotency validation before action.

## Screen 6 — System / Failure View

This can be a compact section, not necessarily a separate navigation route.

Show:

```text
Recent system events
- AI timeout
- Malformed AI response
- Razorpay timeout
- Duplicate event blocked
```

For the final pitch, one failure should be clickable.

---

## Screen 7 — Optional demo control

Only build this if time remains.

A dev/demo-only control can simulate:
- gateway timeout
- already-successful payment
- duplicate event
- low-confidence diagnosis

This is useful for the video, but it must be clearly marked as demo tooling and never be confused with production controls.

---

## MVP navigation

```text
Dashboard
  ├── Recovery Cases
  │     └── Case Detail
  ├── Review Queue
  └── Metrics
```

Do not add settings pages, onboarding flows, profile pages, or a full merchant management suite.

## Manual owner actions

- Pick the final visual theme before coding.
- Implement dashboard and case detail first.
- Populate the UI from real API responses.
- Take screenshots only after the metrics are real.
- Check desktop layout at the exact browser size used in the video.
